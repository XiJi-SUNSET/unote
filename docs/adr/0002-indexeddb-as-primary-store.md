# ADR-0002：用 IndexedDB 作为主存储

- **状态**：Accepted
- **日期**：2026-10-17
- **决策者**：项目作者
- **关联**：[03-data-backup.md](../03-data-backup.md)

## 背景

数据层需要满足：

1. 千条量级笔记的结构化存储、排序、按标签过滤
2. 图片以二进制保存，且要能快速取出渲染
3. 导出时能廉价地遍历全部数据
4. 不引入额外的原生插件（体积、升级风险、构建复杂度）

候选：

1. **IndexedDB（Dexie）**
2. **@capacitor-community/sqlite**
3. **文件系统 + JSON 索引**

## 决策

采用 **IndexedDB（Dexie 4）+ 图片 Blob 同库存储**。

## 理由

1. **零原生依赖**。SQLite 插件会增加 3–5MB，且引入 SQLCipher 分支、ABI 拆分、Gradle 联动等一串构建问题。
2. **Blob 是一等公民**。IndexedDB 直接存 `Blob`，取出即 `URL.createObjectURL()`。走 SQLite 要么存 base64（体积 +33%，且大图会撑爆内存），要么存文件路径——而"路径"会带来一整套权限、URI 编码、跨版本目录变更的问题。
3. **事务与迁移够用**。Dexie 的 `version(n).upgrade()` 覆盖本项目全部迁移需求；没有复杂 JOIN 场景。
4. **导出简单**。一次游标遍历就能拿到全部笔记与图片，直接喂给 fflate。

## 后果

**正面**

- 数据层代码量约为 SQLite 方案的 1/3
- 无 ABI 拆分、无插件升级连带风险
- 在浏览器里也能完整跑起来（便于开发与测试）

**负面**

- **存储清除门槛低**：用户"清除应用数据"或卸载即全丢，比原生文件系统更脆
- 没有 FTS5，全文搜索只能自己做内存索引
- 大 Blob 写入可能触发配额错误，需要在 UI 上处理

**需要持续观察**

- 单库体积超过 500MB 时的读写性能
- 不同 WebView 版本对 Blob 存储的实现差异

## 缓解

| 风险 | 措施 |
|---|---|
| 数据丢失 | 每日本地快照（7 份）+ 导出提醒 + 一键导出 ZIP，见 [03-data-backup.md](../03-data-backup.md) §6 |
| 搜索能力 | 千条量级用内存倒排索引即可；超过阈值再考虑分片 |
| 配额错误 | 写入失败保留内存草稿并提示导出；设置页展示 `navigator.storage.estimate()` |

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| SQLite 插件 | 为 2MB 数据引入 5MB 依赖与一整套原生构建风险，性价比为负 |
| 文件系统 + JSON | 启动时扫描千个文件，每次读都要过 JS 桥，首屏会慢 1–2 秒 |
| localStorage | 5MB 上限、同步阻塞、无法存二进制 |
